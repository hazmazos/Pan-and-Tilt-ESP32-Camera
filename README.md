# Pan-and-Tilt-ESP32-Camera

## Introduction
This project was intended for me to explore computer vision using OpenCV. The idea was to have a pan and tilt camera using 2 SG90 servo motors and an ESP32-S3 board with an OV3660 camera board. Instead as you will see a lot of time was spent setting up the webserver and implementing data streams between devices. The camera capture would be streamed to the client using HTTP initially and then using a local site with interactive sliders you could send pan and/or tilt servo commands back to the ESP32 so it could move the camera.  

Once I got that set up I wanted to improve the camera throughput. To start I had to find a way to measure/approximate the current performance. I did this both on the ESP32 and the client. The client results were the most important as it would reflect the user experience more. The method used is an approximation as instead of recoding the data stream it measures from the time from the start of the request until a jpeg frame is decoded. It is here I should expand a bit on the 2 methods used for the data stream. The initial method of approach was to use a single HTTP  GET request for a single JPEG which would then be displayed on the client site. This would be looped over giving the illusion of video streaming. The issue with this approach is that delay is introduced in sending the request and receiving the request repeatedly. My solution to this was to use MJPEG streaming where single HTTP request is maintained and the data is sent continuously separated by a boundary so that the system knows when each JPEG frame ends. This meant that the method of deploying the server had to be changed from a standard webserver to an asynchronous webserver so the loop does not get blocked by the MJPEG requests blocking any servo commands. Once all of that had been setup successfully I set up a trial of a fixed number of JPEG frames and would print the performance metrics (mean FPS and standard deviation) to compare.

Finally, I wanted to introduce a vision model in the setup. Because the ESP32-S3 has a limited 8MB PSRAM I decided to run the model and processing on my desktop and then the results could be streamed back to the ESP32. The whole reason for the first set up was to emulate this step which was proved useful as I learnt the basics of HTTP get requests from the first model which would help in future instances when I shifted to using MJPEG streaming which required you to write the response headers and bodies yourself.

This was a very hands on project with lots of troubleshooting and learning on the go with some of the concepts. I did try and learn the topics beforehand like in a syllabus - building each step progressing with theory but I found it was very time consuming. Secondly, it did not lead to me being able to apply the theory myself as I only knew the form that was taught to me. On the other hand the method of learning as you go has a huge limitation in that your ignorance can be your downfall as you proceed with what is a correct solution but not the most optimal. I don't think that is too much of an issue as a person never stops learning and I myself still feel this project is unfinished. I have intentions in the future to come back and polish and improve features. The important thing is that you begin a project that interests you and follow it through to the end. Nothing is perfect on the first iteration and that in itself is a lesson to learn, accept and iterate on.
